## Сначала обсудить: безопасность и потенциальная потеря пользовательских данных

### A1. Высокий риск XSS в окне release notes

**Статус 03.11.2026: основной sink исправлен.** Результат `marked.parse` теперь санитизируется через DOMPurify перед `dangerouslySetInnerHTML`; проверка frontend-сборки прошла. CSP по-прежнему выключена (`csp: null`), поэтому это не заменяет долгосрочную настройку строгой политики с проверкой нужных Tauri/blob/media источников.

Исходная находка: `src/components/SettingsModal.tsx` вставлял GitHub release metadata без sanitizer. Это опасно из-за доступного frontend bridge к Tauri IPC.

### A2. Windows `open_url` передавал URL в `cmd.exe`

**Статус 03.11.2026: исправлено.** Команда теперь принимает только HTTP(S), отклоняет control/whitespace/backslash и ambiguous authority, а Windows открывает URL аргументом `explorer.exe` без shell. XSS sink release notes отдельно санитизирован.

Исходный риск: `cmd /c start` интерпретировал shell-метасимволы в URL на Windows.

### A3. Удаление с диска и открытие app-папок — риск пути и рассинхронизации

**Статус 03.11.2026:** ID-based удаление было исправлено ранее; `open_app_folder` теперь отклоняет absolute/parent/prefix components, затем canonicalize-check'ом подтверждает, что целевая папка осталась внутри portable data directory. Команда открывает canonical path как отдельный process argument.

**Исходное состояние аудита:** native-команда принимала `Vec<String>` путей и удаляла их напрямую; frontend продолжал удалять ID из SQLite даже после ошибки файловой операции.

**Изменено в текущей рабочей ветке:** `delete_files_from_disk` теперь принимает ID треков, берёт пути только из `LibraryDb`, проверяет абсолютный путь и аудио-расширение, обрабатывает только обычные файлы, ограничивает native batch 500 ID и возвращает отдельно удалённые, уже отсутствующие и неудачные треки. Frontend использует эти результаты: из БД, UI, очереди и плейлистов удаляются только успешные/уже отсутствующие треки; неудачные остаются в медиатеке и показывается сообщение. Для браузерного режима удаление прекращается с сообщением, а не изображается как успешное. Native-команды и сопутствующая SQLite-логика прошли Windows build/test в Actions run `40166872559`.

Это существенно убирает прямую возможность передать команде произвольный путь и исправляет прежнюю рассинхронизацию. Остаточное ограничение: ID из SQLite остаётся доверенной точкой; команды редактирования metadata по-прежнему принимают путь к файлу, поэтому их серверную валидацию нужно рассматривать отдельно.

### A4. Запись обложки трека могла менять изображения рядом с музыкой

**Статус 03.11.2026: исправлено.** Побочный вызов `sync_folder_cover_art` удалён из пути редактирования тегов: изменение embedded cover больше не переписывает `Folder.jpg` или другие соседние файлы. Ошибка записи embedded artwork должна по-прежнему отображаться как ошибка операции, а не выдавать ложный успех.

Исходный риск состоял в снятии read-only, удалении `AlbumArt*.jpg` и перезаписи `Folder.jpg` при изменении тега.

### A5. TOCTOU при проверке доверенного внешнего плагина

**Статус 03.11.2026: исправлено.** Раньше source fingerprint и исполняемый JavaScript можно было читать отдельными операциями. Загрузка теперь один раз читает bounded manifest/source, вычисляет versioned fingerprint с разделением полей и возвращает именно эти проверенные source bytes; размер manifest и source ограничен. Rust test проверяет изменение fingerprint при изменении source. Windows Actions test для этого изменения добавлен в workflow; новый run ожидает push и пока не выполнен.

Остаточный риск: внешний плагин остаётся пользовательским исполняемым кодом в Web Worker; Worker ограничивает доступ к DOM и Tauri bridge, но не является полноценным sandbox от сетевого доступа, высокой нагрузки CPU/памяти или browser-engine уязвимостей. Пользователь должен включать только доверенные плагины.

## Производительность и ОЗУ

### P1. Виртуализация строк ограничивает DOM, но не данные в памяти

**Основной native-список дополнительно уточнён:** `TrackTable` сохраняет общую виртуальную высоту и запрашивает видимое окно плюс ровно 12 строк overscan сверху и снизу. `App.tsx` загружает exact `offset + limit` диапазон, хранит summaries только активного окна в bounded indexed cache (hard cap 128), а absolute indices сохраняют правильное положение строк. Placeholder использует число результатов из SQLite, а не размер окна; полный COUNT выполняется один раз на поколение запроса. Обложки карточек плейлистов больше не зависят от этого окна: отдельный SQLite-запрос возвращает до восьми cover paths на плейлист без полных track summaries. Выбор диапазона и массовые действия работают по ID.

Проверка отсутствующих файлов также переведена на последовательные SQLite-страницы по 500 строк: память не растёт до размера библиотеки, статусы сохраняются в `is_missing`, а массив модального окна содержит только реально отсутствующие записи. Все native-таблицы теперь используют общий LRU; custom-плейлисты и кастомное избранное читают summaries страницами по сохранённому списку ID. Для фильтрации custom-порядка подгружается только список совпадающих ID, а не все summary. Drag-reorder опирается на полный порядок ID и больше не требует удерживать весь массив треков. Реальную память WebView2 и интерактивную прокрутку всё ещё требуется проверить; синтетический Node-тест не измеряет DOM, изображения или GPU.

### P2. Детектор аудиопиков мог раздувать неограниченную очередь

**Статус 03.11.2026: устранён неограниченный рост.** Audio diagnostics теперь используют `sync_channel(1024)` и неблокирующий `try_send`; переполненные диагностические сообщения отбрасываются, вместо того чтобы блокировать audio callback или расти без лимита. Частоту срабатывания на реальных треках ещё можно профилировать, но эта телеметрия больше не может копить unbounded backlog.

### P3. Декодирование изображений в frontend местами сначала создаёт полный растр

- `src/components/BatchTagEditorModal.tsx:250–293`: изображение целиком читается в Data URL, затем декодируется через `Image`; только после этого уменьшается на canvas до 1200 px. В памяти могут одновременно оказаться исходный `File`, base64-строка, декодированный растр и выходной JPEG; при ошибке canvas возвращается исходный Data URL.
- `src/services/discordRpc.ts:12–56`: для локального/embedded изображения сначала создаётся `Image`, после чего canvas уменьшается до 384 px. Для URL к уже закэшированной обложке путь теперь использует 256px variant (см. вызов около строки 116), что снижает риск; локальный/data URL может всё ещё быть полноразмерным.
- `src/theme/material3.ts:262–289` декодирует переданную картинку в `Image` до рисования на canvas 16×16. Основной вызов в `src/App.tsx:1696` запрашивает 256px variant для cache URL, но для иных типов источников размер не обязательно ограничен.

Это пиковая, а не обязательно постоянная память. Отдельно: native `cover_cache` имеет лимиты источника и использует scaled decode исходника при генерации вариантов; это более безопасный путь и он не опирается только на встроенный thumbnail.

### P4. Не каждый cache-формат получает уменьшенные варианты

`src/utils/coverArt.ts` направляет cache URL на 96/256 вариант. В `src-tauri/src/cover_cache.rs` генерация вариантов ограничена поддерживаемыми decoder-путями JPEG/PNG; для иных форматов endpoint может вернуть оригинал. Это означает, что URL с суффиксом `96`/`256` сам по себе не гарантирует малого ответа. Влияет на реальное потребление RAM/трафика для таких обложек; проверить поддерживаемые MIME и поведение fallback отдельно.

### P5. Настройки памяти — эвристики, не верхний предел процесса

В `src-tauri/tauri.conf.json:29` и `src-tauri/src/lib.rs` задан `--max-old-space-size=256`; для WebView2 также вызывается `SetMemoryUsageTargetLevel` (`lib.rs:1938–2002`). Это может помогать снижать давление на JS/WebView, но не является гарантированным лимитом всего Tauri-процесса: остаются native Rust allocations, декодированные картинки, GPU и общие процессы WebView2. Эффект должен подтверждаться измерениями на Windows, а не выводиться из самих флагов.

## План по ограничению памяти для виртуализированной таблицы — черновик на оценку

**Текущий статус:** native track table (`App.tsx` + `TrackTable.tsx`) запрашивает ровно виртуальное окно с 12 строками overscan с каждой стороны. Exact диапазоны идут через `offset + limit`; кэш сохраняет только текущий диапазон и дополнительно ограничен 128 summaries. Общая виртуальная высота/absolute indices сохраняются. Для поиска placeholder использует общий count текущего SQLite-результата, а не число кэшированных строк; count query выполняется один раз на поколение, последующие диапазоны не пересчитывают его. Custom-порядок и favorites сохраняют ID-порядок. Синтетический тест на 100 000 строк подтверждает exact range, bounded cache и дедупликацию пересекающихся запросов, но не измеряет WebView2/RAM процесса. Отдельное исключение — намеренное формирование полного playback context/очереди при запуске воспроизведения всего списка.

### Этап 1. Синтетические данные и исходные замеры

- **Выполнено:** тесты генерируют 100 000 лёгких синтетических записей без файлов и проверяют bounded page/indexed cache, exact range loading, пересекающиеся запросы и абсолютные индексы; пользовательскую медиатеку не сканируют.
- **Осталось:** измерить реальную память/отзывчивость WebView2 на Windows; текущий Node-тест подтверждает ограничение структуры данных, но не измеряет память приложения, DOM, картинки или GPU.
- Не менять целевые уровни памяти/лимиты процесса на основании одного синтетического теста.

### Этап 2. Контракты и зависимости от полного массива

- **Выполнено частично:** основная native-таблица, абсолютные индексы строк, shift-select по диапазону из SQLite и загрузка выбранных треков для массовых операций используют ограниченный кэш/ID.
- **Выполнено:** проверка существования файлов для нативной библиотеки проходит по SQLite-страницам по 500 записей, обновляет статусы и не зависит от того, какие строки остались в LRU-кэше. Во время сканирования новые пути сверяются с missing-записями на каждой партии; при совпадении сохраняется исходный ID. Первичное окно отсутствующих треков показывается только после завершающего startup scan, а не во время проверки устаревших путей.
- **Каталог очищен от старой схемы:** native startup больше не читает `library.json`/`arachnid_data.json` и не выполняет миграцию их трековых записей. SQLite — единственный каталог; path/ID связки берутся из текущих M3U8, а прежняя временная legacy map удаляется при открытии БД.
- **Выполнено дополнительно:** импорт M3U в native bounded view строит порядок из DB IDs и обновляет окно таблицы без добавления всего импортированного списка в кэш; перезагрузка metadata/lyrics получает вытесненные записи по ID чанками; импорт существующего пути сверяется с SQLite до сканирования, а поиск missing-записи для переноса выполняется в SQLite по title/artist и сохраняет исходный ID, избранное, счётчик воспроизведений и дату добавления — оба сценария работают независимо от eviction.
- **Осталось проверить:** взаимодействия клавиатуры/быстрого скролла в Windows WebView2.
- Drag-reorder сохранён без полного массива summaries: компонент получает полный ordered ID list, а summaries остаются в LRU-кэше.

### Этап 3. Range/page provider и bounded cache

- **Выполнено:** основной каталог и коллекционные представления загружаются SQLite-диапазонами; custom-плейлисты и custom favorites берут страницы из ID-порядка. Native SQL сортирует/фильтрует custom ID list (с сохранением повторов и порядка равных значений), после чего таблица запрашивает summaries порциями; общая виртуальная высота сохраняется.
- Для основного списка кэш дедуплицирует перекрывающиеся запросы по абсолютному индексу, игнорирует устаревшие поколения и удерживает только активный диапазон (hard cap 128 summaries); полный `COUNT(*)` вычисляется только при первом запросе нового поколения, следующие range-запросы пропускают пересчёт. Drag-reorder использует полный ID order, а не кэшированные строки.
- **Исправлено:** native page loader больше не зависит от `nativeTrackTotal` и других значений, не нужных bounded-ветке. Ранее изменение total меняло identity callback, повторно запускало reset-effect и очищало таблицу «Все треки» после её загрузки.
