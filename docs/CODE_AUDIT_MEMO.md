## Сначала обсудить: безопасность и потенциальная потеря пользовательских данных

### A1. Высокий риск XSS в окне release notes

`src/components/SettingsModal.tsx:1498–1504` вставляет результат `marked.parse(latestRelease.body)` в `dangerouslySetInnerHTML`. В просмотренной цепочке санитайзер/allowlist HTML не обнаружен. Текст приходит из GitHub release metadata; CSP в `src-tauri/tauri.conf.json:33` выключена (`csp: null`). Если внедрённая разметка сможет выполнить скрипт в WebView, последствия особенно серьёзны из-за доступного frontend bridge к Tauri IPC. Нужна отдельная проверка всех `marked` опций, происхождения metadata и разрешений IPC; до неё считать поверхность опасной.

### A2. Windows `open_url` передаёт URL в `cmd.exe`

`src-tauri/src/lib.rs:3094–3110`: Windows-ветка формирует `cmd /c start "" <url>` без строгой схемы/host allowlist и без безопасного обхода командной оболочки. Символы, интерпретируемые `cmd.exe`, потенциально превращают открытие URL в запуск команды. Риск зависит от источника строки; связка с release metadata/XSS повышает приоритет. На других ОС используется `xdg-open` с отдельным аргументом, поэтому этот конкретный shell-риск относится к Windows.

### A3. Удаление с диска — риск произвольного пути и рассинхронизации

**Исходное состояние аудита:** native-команда принимала `Vec<String>` путей и удаляла их напрямую; frontend продолжал удалять ID из SQLite даже после ошибки файловой операции.

**Изменено в текущей рабочей ветке:** `delete_files_from_disk` теперь принимает ID треков, берёт пути только из `LibraryDb`, проверяет абсолютный путь и аудио-расширение, обрабатывает только обычные файлы, ограничивает native batch 500 ID и возвращает отдельно удалённые, уже отсутствующие и неудачные треки. Frontend использует эти результаты: из БД, UI, очереди и плейлистов удаляются только успешные/уже отсутствующие треки; неудачные остаются в медиатеке и показывается сообщение. Для браузерного режима удаление прекращается с сообщением, а не изображается как успешное. Native-команды и сопутствующая SQLite-логика прошли Windows build/test в Actions run `40166872559`.

Это существенно убирает прямую возможность передать команде произвольный путь и исправляет прежнюю рассинхронизацию. Остаточное ограничение: ID из SQLite остаётся доверенной точкой; это не заменяет системное разрешение/подтверждение и не исправляет другие IPC-команды с прямыми путями (например, `open_app_folder` ниже и операции записи тегов). Вся поверхность IPC остаётся важной в контексте A1.

Отдельный риск: `open_app_folder` (`src-tauri/src/lib.rs:3071–3092`) присоединяет `subfolder` к portable directory без проверки `..`/абсолютного пути, создаёт целевой каталог и открывает его. Команды редактирования metadata также принимают путь к файлу и записывают в него; их ожидаемый frontend-путь использования не заменяет серверную валидацию аргументов.

### A4. Запись обложки трека может удалять/перезаписывать изображения рядом с музыкой

`src-tauri/src/lib.rs:1124–1162` и `1503–1507`: при явном сохранении новой обложки `sync_folder_cover_art` снимает read-only атрибут и удаляет `AlbumArt*.jpg`, затем записывает/перезаписывает `Folder.jpg` в папке файла. Комментарий о сохранении пользовательских folder-cover файлов расходится с фактической перезаписью `Folder.jpg`; `cover.jpg` отдельно не удаляется, но `Folder.jpg` всё равно может быть заменён.

Это затрагивает соседние с музыкой изображения и потенциально уничтожает пользовательский файл. Также расходится с текущим пользовательским ограничением не изменять изображения рядом с музыкальными файлами. Ничего не запускалось и файлы не трогались в ходе аудита.

## Производительность и ОЗУ

### P1. Виртуализация строк ограничивает DOM, но не данные в памяти

**Основной native-список исправлен:** `TrackTable` сохраняет общую виртуальную высоту, но `App.tsx` держит только восемь SQLite-страниц по 300 summary (до 2 400 записей). Видимый диапазон и соседи догружаются по требованию; абсолютные индексы позволяют не терять позицию строк после вытеснения страниц. Выбор диапазона и массовые действия работают по ID.

Проверка отсутствующих файлов также переведена на последовательные SQLite-страницы по 500 строк: память не растёт до размера библиотеки, статусы сохраняются в `is_missing`, а массив модального окна содержит только реально отсутствующие записи. Все native-таблицы теперь используют общий LRU; custom-плейлисты и кастомное избранное читают summaries страницами по сохранённому списку ID. Для фильтрации custom-порядка подгружается только список совпадающих ID, а не все summary. Drag-reorder опирается на полный порядок ID и больше не требует удерживать весь массив треков. Реальную память WebView2 и интерактивную прокрутку всё ещё требуется проверить; синтетический Node-тест не измеряет DOM, изображения или GPU.

### P2. Детектор аудиопиков отправляет сообщение на каждый превышающий порог сэмпл

`src-tauri/src/player.rs:160–179`: горячий аудиопуть создаёт и отправляет `GlitchReport` каждый раз, когда `delta > 14000`; канал создаётся через неограниченный `std::sync::mpsc::channel` (`~524`). Агрегация происходит на принимающей стороне (`~1305`), то есть после очереди. На ударном/высокочастотном материале порог может давать много сообщений, вызывая лишнюю работу/аллокации и потенциальный временный рост очереди. Реальные частоты срабатывания и влияние на аудиопоток не измерялись; сначала нужен профилирующий тест на реальных треках.

### P3. Декодирование изображений в frontend местами сначала создаёт полный растр

- `src/components/BatchTagEditorModal.tsx:250–293`: изображение целиком читается в Data URL, затем декодируется через `Image`; только после этого уменьшается на canvas до 1200 px. В памяти могут одновременно оказаться исходный `File`, base64-строка, декодированный растр и выходной JPEG; при ошибке canvas возвращается исходный Data URL.
- `src/services/discordRpc.ts:12–56`: для локального/embedded изображения сначала создаётся `Image`, после чего canvas уменьшается до 384 px. Для URL к уже закэшированной обложке путь теперь использует 256px variant (см. вызов около строки 116), что снижает риск; локальный/data URL может всё ещё быть полноразмерным.
- `src/theme/material3.ts:262–289` декодирует переданную картинку в `Image` до рисования на canvas 16×16. Основной вызов в `src/App.tsx:1696` запрашивает 256px variant для cache URL, но для иных типов источников размер не обязательно ограничен.

Это пиковая, а не обязательно постоянная память. Отдельно: native `cover_cache` имеет лимиты источника и использует scaled decode исходника при генерации вариантов; это более безопасный путь и он не опирается только на встроенный thumbnail.

### P4. Не каждый cache-формат получает уменьшенные варианты

`src/utils/coverArt.ts` направляет cache URL на 96/256 вариант. В `src-tauri/src/cover_cache.rs` генерация вариантов ограничена поддерживаемыми decoder-путями JPEG/PNG; для иных форматов endpoint может вернуть оригинал. Это означает, что URL с суффиксом `96`/`256` сам по себе не гарантирует малого ответа. Влияет на реальное потребление RAM/трафика для таких обложек; проверить поддерживаемые MIME и поведение fallback отдельно.

### P5. Настройки памяти — эвристики, не верхний предел процесса

В `src-tauri/tauri.conf.json:29` и `src-tauri/src/lib.rs` задан `--max-old-space-size=256`; для WebView2 также вызывается `SetMemoryUsageTargetLevel` (`lib.rs:1938–2002`). Это может помогать снижать давление на JS/WebView, но не является гарантированным лимитом всего Tauri-процесса: остаются native Rust allocations, декодированные картинки, GPU и общие процессы WebView2. Эффект должен подтверждаться измерениями на Windows, а не выводиться из самих флагов.

## Функциональные и корректностные находки

### F1. Equalizer UI подключён к пустым методам, визуализатор синтетический

`src/services/audioEngine.ts:500–514`: `getVisualizerData()` вычисляет синусоидальную анимацию от времени, не получает спектр аудиосигнала; `setEqGain()` и `applyEqPreset()` пустые. При этом `src/components/EqualizerModal.tsx` вызывает оба EQ-метода. Поэтому UI может показывать настройки/реакцию, которые не меняют звук, и визуализатор не отображает аудио. Проверить, считается ли это недореализованной функцией или временной заглушкой.

### F2. Сортировка жанров опирается на длину массива ID

`src-tauri/src/library_db.rs:315–316`: жанры сортируются по `track_ids.len()`. При вызове с `include_track_ids == false` (`~296`) все длины равны нулю и сортировка фактически становится алфавитной, даже если ожидается сортировка по числу треков. Проверить вызовы и ожидаемое поведение; правильный счётчик уже отдельно есть в `track_count`.

### F3. Неиспользуемый placeholder IPC

`src-tauri/src/lib.rs:1628–1632`, `batch_update_tags`, только возвращает `tracks.len()` и не изменяет metadata; в просмотренном frontend прямых вызовов не найдено. Похоже на устаревшую/недоделанную команду, но следует проверить внешние/legacy invoke-вызовы, прежде чем удалять.

### F4. Типизация TypeScript не строгая

`tsconfig.json:14` отключает `strict`; также отключены проверки unused locals/parameters. Успешный `tsc` подтверждает компиляцию текущей конфигурации, но не строгую null/type safety и не отсутствие мёртвого кода. Это не самостоятельная ошибка, но снижает ценность сборки как статической проверки.

### F5. Слишком крупные компоненты усложняют сопровождение

Ветка содержит крупные модули с несколькими зонами ответственности: `src/App.tsx` (~5533 строк), `src-tauri/src/lib.rs` (~3428), `src/components/SettingsModal.tsx` (~3136), `PlaylistsGridView.tsx` (~1882), `MiniPlayer.tsx` (~1639). Это повышает стоимость локальных изменений и риск регрессий; конкретное разбиение — отдельное решение, не предлагается выполнять в ходе аудита.

## План по ограничению памяти для виртуализированной таблицы — черновик на оценку

**Текущий статус:** LRU-кэш подключён ко всем native-таблицам (`App.tsx` + `TrackTable.tsx`): основной каталог использует SQLite `offset + limit`, пользовательские плейлисты и кастомное избранное — страницы по сохранённому порядку ID. Общая виртуальная высота/абсолютные индексы сохраняются, кэш ограничен восемью страницами по 300 summary (до 2 400 записей). Shift-выделение и drag-reorder опираются на ID; фильтрованный/отсортированный custom-порядок вычисляется SQL-проекцией списка ID без загрузки полных summary. Синтетический тест создаёт каталог из 100 000 строк и проверяет предел кэша/индексацию, но пока не измеряет WebView2/RAM процесса. Отдельное исключение — намеренное формирование полного playback context/очереди при запуске воспроизведения всего списка: ограничение таблицы не ограничивает объём этой очереди.

### Этап 1. Синтетические данные и исходные замеры

- **Выполнено частично:** тест генерирует 100 000 лёгких синтетических записей без файлов и проверяет LRU/индексацию; максимум в кэше — восемь страниц по 300 (2 400 записей). Пользовательскую медиатеку тест не сканирует.
- **Осталось:** измерить реальную память/отзывчивость WebView2 на Windows; текущий Node-тест подтверждает ограничение структуры данных, но не измеряет память приложения, DOM, картинки или GPU.
- Не менять целевые уровни памяти/лимиты процесса на основании одного синтетического теста.

### Этап 2. Контракты и зависимости от полного массива

- **Выполнено частично:** основная native-таблица, абсолютные индексы строк, shift-select по диапазону из SQLite и загрузка выбранных треков для массовых операций используют ограниченный кэш/ID.
- **Выполнено:** проверка существования файлов для нативной библиотеки проходит по SQLite-страницам по 500 записей, обновляет статусы и не зависит от того, какие строки остались в LRU-кэше.
- **Выполнено дополнительно:** импорт M3U в native bounded view строит порядок из DB IDs и обновляет окно таблицы без добавления всего импортированного списка в кэш; перезагрузка metadata/lyrics получает вытесненные записи по ID чанками; импорт существующего пути сверяется с SQLite до сканирования, а поиск missing-записи для переноса выполняется в SQLite по title/artist и сохраняет исходный ID, избранное, счётчик воспроизведений и дату добавления — оба сценария работают независимо от eviction.
- **Осталось проверить:** взаимодействия клавиатуры/быстрого скролла в Windows WebView2.
- Drag-reorder сохранён без полного массива summaries: компонент получает полный ordered ID list, а summaries остаются в LRU-кэше.

### Этап 3. Range/page provider и bounded cache

- **Выполнено:** основной каталог и коллекционные представления загружаются SQLite-диапазонами; custom-плейлисты и custom favorites берут страницы из ID-порядка. Native SQL сортирует/фильтрует custom ID list (с сохранением повторов и порядка равных значений), после чего таблица запрашивает summaries порциями; общая виртуальная высота сохраняется.
- Кэш дедуплицирует одинаковые запросы, игнорирует устаревшие поколения и ограничен 8×300 summaries; drag-reorder использует полный ID order, а не кэшированные строки.
- **Осталось:** проверить быстрые скачки scrollbar/гонки ответов в Tauri/WebView2; полный playback queue при запуске всего списка остаётся отдельным от кэша.

### Этап 4. Действия с диапазонами и ID

- **Выполнено частично:** shift-select запрашивает ID выбранного диапазона; массовые операции загружают summary выделенных ID отдельно; keyboard up/down адресует абсолютный индекс и загружает нужную страницу.
- **Осталось вручную/через тесты проверить:** контекстное меню, пакетные теги, очередь, удаление/избранное при выделении после eviction, смену фильтра во время запроса и отсутствие пустого-state flash.
- Drag-reorder для плейлистов/favorites строит reorder из полного ID-порядка и сохраняет проверки на полный размер последовательности; корректность реального перетаскивания проверить на Windows.
