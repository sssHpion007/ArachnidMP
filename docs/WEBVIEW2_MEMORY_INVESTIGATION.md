# WebView2: расследование потребления памяти в ArachnidMP

**Дата:** 24 октября 2026 г.  
**Область:** исходники текущей ветки `arena/6fcee020-arachnidmp` и предоставленный пользователем снимок Windows-процессов.  
**Итог в одном предложении:** в снимке почти вся память процесса приходится на WebView2, но одного снимка недостаточно, чтобы назвать это утечкой; наиболее проверяемый риск в коде — продолжение активности скрытых WebView из-за глобально отключённых Chromium backgrounding/throttling при сохранении дополнительных окон.

## 1. Краткое резюме

В предоставленном снимке дерево ArachnidMP состоит из 8 процессов, доступных для чтения; суммарно это около **495,1 MiB Working Set**, **464,1 MiB Private Bytes** и **178,8 MiB Private Working Set**. На процессы WebView2 приходится приблизительно **456 MiB / 451 MiB / 169 MiB** соответственно, а на native-процесс ArachnidMP — **39 MiB / 12,9 MiB / 9,6 MiB**.

Это подтверждает, что в данном измерении основная память находится в Chromium/WebView2, а не в Rust-процессе плеера. Оно **не подтверждает утечку**: нет временного ряда, контрольного состояния «только главное окно», идентификации типов WebView2-процессов и синхронных данных JS heap. Большой Chromium footprint может включать browser, renderer, GPU и служебные процессы, кэш изображений/декодирования и прочую native-память, не отражаемую `performance.memory`.

В коде выявлены следующие существенные факторы:

1. **Сильный кандидат на проверку:** Windows-запуск глобально задаёт `--disable-background-timer-throttling`, `--disable-renderer-backgrounding`, `--disable-backgrounding-occluded-windows` и `--disable-features=CalculateNativeWinOcclusion` (`src-tauri/src/lib.rs`, около строк 2671–2679). Это может не давать скрытым/перекрытым WebView перейти в обычный фоновой режим. Прежде всего это объясняет продолжающуюся активность и потенциально замедленное освобождение ресурсов, но **само по себе не доказывает рост памяти**.
2. В приложении есть отдельные WebView-окна для lyrics, track details и equalizer. После скрытия они **сохраняются**, а не уничтожаются; код просит WebView перейти на LOW memory target. Это разумная функциональная стратегия для быстрого повторного открытия, но она оставляет их renderer/DOM и потенциальный кэш существовать.
3. LOW target — подсказка/цель с best-effort поведением, не жёсткий лимит и не команда завершить renderer. На скрытых страницах скрипты могут продолжаться; в частности, общие browser flags ослабляют штатное фоновое ограничение.
4. Аргумент `--max-old-space-size=256` у трёх вспомогательных окон ограничивает старое поколение V8, **а не общий RSS/Private Bytes WebView2**. Он не ограничивает native, GPU, изображения и другие части процесса.
5. В просмотренных компонентах нет явного доказательства утечки слушателей или постоянно работающей анимации во всех companion windows. Видны обычные очищаемые listeners/timers; это снижает приоритет такой гипотезы, но не исключает утечки в остальных частях приложения.

**Рекомендация:** пока не менять браузерные аргументы и не закрывать окна принудительно только на основании одного числа. Сначала провести контролируемый A/B-тест фоновых флагов и получить временной ряд с привязкой WebView label → PID/process kind. Это даст больше диагностической ценности и не рискует нарушить воспроизведение, hotkeys/media keys или поведение окон.

## 2. Что именно показывает имеющийся снимок

| Область | Working Set | Private Bytes | Private Working Set |
|---|---:|---:|---:|
| Всё дерево ArachnidMP (8/8 процессов, inaccessible=0) | 495,1 MiB | 464,1 MiB | 178,8 MiB |
| WebView2-процессы, суммарно | ~456 MiB | ~451 MiB | ~169 MiB |
| Native-процесс ArachnidMP | ~39 MiB | ~12,9 MiB | ~9,6 MiB |

По этому снимку WebView2 даёт примерно **92% суммарного Working Set**, **97% Private Bytes** и **95% Private Working Set** дерева. Самый крупный отдельный WebView2 PID в исходном снимке имел около **268,7 MiB Private Bytes / 72,8 MiB Private Working Set**; другой крупный — около **110,2 / 48 MiB**. Имена процессов и PID известны, однако их роли (browser/renderer/GPU/utility), соответствующие WebView и отображаемые окна — нет.

### Как читать эти три метрики

- **Working Set (WS)** — страницы, сейчас находящиеся в физической памяти; включает shared pages. При суммировании процессов одни и те же разделяемые страницы могут учитываться более одного раза, поэтому сумма WS дерева не равна точному объёму уникальной физической RAM, занятой приложением.
- **Private Bytes** (`PrivateUsage`) — приватная committed memory процесса, а не объём находящейся в RAM памяти. Для вывода о реальном резидентном потреблении его нужно читать вместе с private working set.
- **Private Working Set** — резидентные приватные страницы процесса. В этом снимке совокупное значение WebView2 около 169 MiB заметно ниже 451 MiB Private Bytes.

Поэтому формулировка «ArachnidMP использует около 495 MiB ОЗУ» слишком груба: это сумма WS процесса-дерева с учётом shared pages. Более аккуратное описание снимка: *дерево имеет около 495 MiB суммарного WS и около 179 MiB суммарного private WS; около 169 MiB private WS относятся к процессам WebView2*.

## 3. Архитектура процессов и окон

ArachnidMP — Tauri-приложение с WebView2. В дополнение к главному окну оно может создавать отдельные WebView-окна `lyrics`, `track-details` и `equalizer` (`src-tauri/src/lib.rs`, примерно строки 1961–2126). Companion windows создаются по требованию, а затем обычно скрываются и переиспользуются; скрытие не означает уничтожение DOM, JS heap или самого WebView.

WebView2 использует многопроцессную архитектуру: browser, renderers и служебные процессы; renderer не обязательно соответствует одному окну. Поэтому число `msedgewebview2.exe` нельзя напрямую перевести в число открытых окон. Родительская связь в Windows process tree также не всегда отвечает на вопрос, какой WebView или контент обслуживает конкретный renderer.

Текущая native-диагностика (`src-tauri/src/memory_diagnostics.rs`) делает снимок дерева дочерних процессов ArachnidMP, собирает WS/Private Bytes/Private WS и группирует WebView2 по имени процесса. Это полезно для ответа «какая часть дерева занимает память», но **не содержит WebView process kind и сопоставления PID с label окна**. В лог также не попадают командные строки процессов.

Отдельные окна получают `SetMemoryUsageTargetLevel(LOW)` при скрытии и `NORMAL` при показе. Главное окно переводится в LOW при переходе в mini mode и обратно в NORMAL при выходе (`set_webview_memory_target` в `lib.rs`, вызовы в `App.tsx`). Код логирует результат установки target. Важно: успешный вызов говорит, что target установлен, а не что память уже освобождена или что renderer приостановлен.

## 4. Конкретные факторы риска в коде

### 4.1. Отключение фонового throttling/backgrounding — приоритетный эксперимент

В Windows startup задаются глобальные аргументы WebView2:

- `--disable-background-timer-throttling`
- `--disable-renderer-backgrounding`
- `--disable-backgrounding-occluded-windows`
- `--disable-features=CalculateNativeWinOcclusion`

Они имеют более широкую область действия, чем одно окно. Если companion window скрыто, либо главное окно перекрыто/свернуто, связанные WebView могут продолжать таймеры/работу в условиях, отличающихся от стандартной политики Chromium. Это особенно важно потому, что скрытые окна живут дальше.

**Что подтверждено кодом:** аргументы действительно задаются глобально для WebView2.  
**Чего это не доказывает:** что именно они породили 451 MiB Private Bytes или вызвали утечку. Также нельзя предполагать, что все флаги безопасно удалить: playback, media session, media keys, автоматическое воспроизведение и скрытый mini-player должны пройти регрессионную проверку.

### 4.2. Сохранение вспомогательных окон после закрытия/скрытия

Lyrics, EQ и details реализованы как отдельные frontend entry modes. При закрытии окна событие обычно отменяет физическое закрытие и просит главное окно скрыть companion; при повторном открытии используется уже созданное окно. Native hide-команды устанавливают LOW target, но не уничтожают WebView. Это может создавать **устойчивый стартовый/платформенный overhead**, даже если пользователь сейчас смотрит только главное окно. Сравнить «никогда не открывал companion» и «открыл, затем скрыл» — важный тест.

Для lyrics есть 500-миллисекундный retry timer до получения первого состояния и обработчик progress; таймер прекращается после получения state, а listeners очищаются при unmount. В EQ и details аналогично есть кратковременный retry до первого state и cleanup. В просмотренных файлах это не выглядит как очевидный бесконечный listener/timer leak. При этом скрытая страница остаётся смонтированной, и общий Chromium-процесс может удерживать её ресурсы.

### 4.3. JS heap — только часть памяти

`src/main.tsx` записывает `performance.memory` раз в 30 секунд с label текущего окна (`main`, `lyrics`, `track-details`, `equalizer`), если API доступен в используемом Runtime. Это полезная телеметрия JS heap, но она не включает всю native-память Chromium, графические поверхности, декодированные изображения и все кэши. В доступном фрагменте предоставленных логов значений `MEMORY_JS_HEAP` нет, поэтому сейчас нельзя утверждать, что JS heap растёт либо стабилен.

`--max-old-space-size=256` встречается при создании трёх дополнительных окон. Это лимит V8 old space, а не 256 MiB на весь процесс и не потолок приватной памяти. Низкий/стабильный JS heap при растущем Private Bytes будет указывать на поиск вне обычного JS heap; это не оправдывает автоматически ни Chromium, ни native-код.

### 4.4. UI, коллекции, обложки и анимация: вторичный кандидат

В главном UI коллекции держат в памяти модели треков и индексы группировки (`libraryCollectionIndex.ts`); картинки могут добавлять декодированные поверхности и кэш Chromium. В `PlaylistsGridView.tsx` и `MiniPlayer.tsx` есть lazy/async-загрузка обложек и виртуализированные карточки/списки, что ограничивает одновременную отрисовку; некоторые режимы обложек показывают несколько изображений на карточке. Это означает, что объём библиотеки и обложек надо фиксировать в тестах, но просмотренный код **не показывает очевидную загрузку всех изображений в один момент**.

`NowPlayingBar` использует visualizer с `requestAnimationFrame`, ограниченный примерно 15 FPS и включаемый только при воспроизведении и ширине окна от 1280 px (`NowPlayingBar.tsx`, около строки 184). При mini-размере условие выключает этот цикл. Это может влиять на CPU/активность при полноразмерном воспроизведении, но сам код не является сильным объяснением постоянного роста памяти.

Имеющиеся логи о количестве треков/групп — важная характеристика нагрузки, но не доказательство утечки. Около 748 группированных треков, отражённых в предоставленных логах, сами по себе не позволяют вывести занимаемый объём: нужны фактический объём строк/обложек и сравнение при одинаковой библиотеке.

## 5. Утечка или обычное потребление Chromium?

### Что можно заключить сейчас

- В конкретный момент WebView2 — доминирующий потребитель памяти в process tree.
- В дереве есть несколько WebView2-процессов с различным объёмом памяти; это ожидаемо для многопроцессного Chromium и не является признаком утечки само по себе.
- Самый крупный WebView2 process имеет заметно больше Private Bytes, чем private resident memory. Значит, число commit нельзя интерпретировать как равный объём физической RAM.
- Snapshot был единичным. Он не отвечает, росли ли метрики с течением времени, уменьшались ли после скрытия окон, или отличаются ли от свежего запуска.

### Что пока неизвестно

1. Был ли снимок сделан сразу после запуска или после продолжительной работы; сколько окон к тому времени открывали.
2. Растут ли Private Bytes и private WS монотонно при неизменной нагрузке, достигают плато или освобождаются после GC/pressure.
3. Какой PID принадлежит browser/renderer/GPU/utility и какие окна/frames им обслуживаются.
4. Были ли одновременно стабильны JS heap и native process memory; значения `MEMORY_JS_HEAP` не предоставлены.
5. Сколько памяти обусловлено библиотекой, изображениями, разрешением экрана, Runtime/WebView2 version, аппаратным ускорением и содержимым страниц.

### Практический критерий утечки

Для подозрения на утечку нужно повторяемое **постепенное увеличение живой памяти** при одном и том же наборе окон/данных/действий и отсутствие плато после стабилизации. Рост должен воспроизводиться на нескольких циклах и переживать нормальное освобождение краткоживущих объектов. Краткий скачок при создании окна, загрузке альбома или первом открытии окна сам по себе не утечка. Изменения WS без сопоставимых изменений private WS тоже могут быть обычной сменой резидентности/общих страниц.

## 6. План измерений

### Этап A — повторяемые сценарии без изменений кода

На одной версии приложения, одной библиотеке, одинаковом экране/масштабе и одинаковом режиме воспроизведения выполнить отдельные запуски:

1. **Cold/main only:** перезапустить приложение; не открывать lyrics/EQ/details; записать состояние после прогрева UI и затем через 1, 5, 10 и 20 минут простоя.
2. **Companion lifecycle:** отдельно для каждого окна открыть его, подождать 2 минуты, скрыть/закрыть штатным способом, подождать 5–10 минут; сравнить с main-only. Повторить несколько раз, не меняя содержимое библиотеки.
3. **Window modes:** full → mini → full, отдельно без воспроизведения и с воспроизведением. Фиксировать память до перехода и после стабилизации, а не только на кадре анимации.
4. **UI workload:** прокрутить большие коллекции, открыть/переключить плейлисты с обложками, затем оставить приложение без действий. Сравнить с idle baseline.
5. Для каждого сценария фиксировать версию приложения, Edge WebView2 Runtime, число и label созданных окон, число треков/обложек, состояние playback и время после старта.

### Этап B — получить сопоставимую диагностику

- Сохранять имеющиеся снимки `MEMORY` с интервалом и `MEMORY_JS_HEAP`, объединяя их по timestamp. Строить отдельные временные линии по Working Set, Private Bytes и Private Working Set; не заменять одну метрику другой.
- На Windows открыть **WebView2/Edge Browser Task Manager** и зафиксировать память по browser/renderer/GPU процессам. Для выбранных страниц использовать DevTools Memory: heap snapshot до и после сценария, сравнение retained objects и allocation timeline.
- Если график private memory растёт, а heap snapshots стабильны, снять Windows Performance Recorder/ETW trace и исследовать native allocations/графические ресурсы; heap snapshot JavaScript такой рост не объяснит.
- Для повышения точности расширить диагностику связью `WebView window label → WebView process info → PID/process kind`; Runtime API `GetProcessInfos` даёт PID/kind, а расширенные process infos в поддерживаемом Runtime позволяют связать renderer с frames. Учитывать, что общий renderer всё равно может обслуживать несколько frames.

Нынешняя диагностика уже пишет process details и `MEMORY_JS_HEAP` по label, но эти два потока не связывает PID с label окна. Частота 30 секунд годится для тренда минутного масштаба, но отдельный запуск может потребовать более частых точек вокруг open/hide/close, чтобы выделить стоимость lifecycle.

### Этап C — изолировать влияние browser flags

Сравнить текущую сборку с контрольной конфигурацией без background overrides, не меняя UI, Runtime и библиотеку. В диагностической сборке ArachnidMP для этого добавлен безопасный переключатель: по умолчанию поведение не меняется; только если переменная `ARACHNIDMP_WEBVIEW_BACKGROUNDING` равна `default`, четыре background-флага не передаются WebView2. В лог пишется `WEBVIEW_CONFIG background_policy=runtime-default` либо `legacy-unthrottled`.

PowerShell, диагностический запуск Portable EXE:

```powershell
$env:ARACHNIDMP_WEBVIEW_BACKGROUNDING = "default"
& ".\\Arachnid-Portable.exe"
```

Контрольный запуск — закрыть приложение полностью, удалить эту переменную из окружения и запустить EXE без неё:

```powershell
Remove-Item Env:ARACHNIDMP_WEBVIEW_BACKGROUNDING -ErrorAction SilentlyContinue
& ".\\Arachnid-Portable.exe"
```

В каждой конфигурации повторить main-only и companion lifecycle сценарии. Проверить playback в mini mode, media keys/session, autoplay, сворачивание/перекрытие и возврат окна. Сравнивать не только пик, но и установившееся значение/наклон графика после 5–20 минут. Если общий тест покажет значимую разницу, следующим шагом изолировать влияние каждого флага отдельно; если флаг нужен для функциональности, искать минимальный набор аргументов или адресные решения вместо безусловного удаления всех флагов.

## 7. Приоритетные варианты оптимизации

### P0 — сначала измерить, затем править

**Добавить сопоставление window label ↔ PID/process kind и записывать состояние окон рядом с памятью.** Это самый дешёвый способ определить, какой процесс растёт. Собирать по возможности отдельные metrics per-process и сохранить агрегаты для совместимости. Не выводить PID конкретного окна из одного только parent PID.

### P1 — проверить и сузить глобальные background overrides

Это наиболее сильная кодовая гипотеза. После A/B-теста удалить только флаги, отсутствие которых не ломает нужную функциональность, или оставить только действительно необходимый набор. Особенно важно проверить скрытые companion windows и полноразмерное/mini playback. Ожидаемый прямой эффект — прежде всего снижение фоновой работы; уменьшение памяти должно быть подтверждено измерениями, а не предполагаться.

### P2 — политика времени жизни скрытых окон

Если сценарии покажут, что именно скрытые companion windows удерживают существенную память, рассмотреть освобождение/пересоздание давно неиспользуемых окон либо явный сброс тяжёлого содержимого при скрытии. Это компромисс между памятью, скоростью повторного открытия и восстановлением состояния. Не закрывать их принудительно до измерений: текущая стратегия явно переиспользует окна, а закрытие может затронуть lyrics/EQ/details UX.

### P3 — оптимизировать только подтверждённый renderer/страницу

Если растёт `usedJSHeapSize` конкретного label — heap snapshot и retainers покажут источники: забытые subscriptions, кеши/длинные массивы, замыкания. Если растут Browser Task Manager native memory или private bytes без роста JS heap — исследовать изображения, GPU surfaces, native allocations и WebView lifecycle через ETW. Для коллекций оценивать число фактически смонтированных карточек и декодированных изображений до введения новых ограничений: существующая виртуализация уже помогает.

### P4 — не считать LOW и V8 limit решениями сами по себе

Оставить LOW target как возможную подсказку Chromium, но не считать его очисткой или hard cap. Не уменьшать `--max-old-space-size` в надежде ограничить общий WebView footprint: это может вызвать более частые GC/ухудшить UX и не задаёт предел native-памяти. Использовать target/heap limit только после измерения нужного эффекта.

## 9. Вывод и статус проверки

A/B-переключатель фоновой политики добавлен в код с сохранением текущего поведения по умолчанию. Windows CI run [#40080729566](https://github.com/sssHpion007/ArachnidMP/actions/runs/40080729566) успешно собрал приложение, прошёл startup/lyrics smoke test и native test suites. Это подтверждает сборку и базовый запуск новой версии, но **не измеряет RAM-разницу между двумя режимами**: фактический memory A/B ещё не проводился.

Наиболее точное заключение по имеющимся данным: **WebView2 объясняет подавляющую часть памяти process tree в предоставленном snapshot, но факт утечки не установлен.** У ArachnidMP есть конкретный, проверяемый механизм, способный поддерживать фоновую работу скрытых WebView: глобально выключенные background timer throttling и renderer/occlusion backgrounding в сочетании с переиспользуемыми скрытыми окнами. Это хорошая первая гипотеза для контролируемого A/B-теста, но пока не доказанная причина цифры 451 MiB Private Bytes.

Следующее инженерно обоснованное действие — получить временные ряды с атрибуцией PID/kind/окна и выполнить сравнение background flags при одинаковом сценарии. Затем оптимизировать ровно тот слой, где будет виден рост: JS heap, WebView native memory, процессы GPU/изображений или стоимость удерживаемых окон.
